# PRD: 교내 분실물 등록 및 확인 서비스

## 1. 5W1H 표
| 구분 | 내용 |
|---|---|
| **Who (누가)** | 교직원 및 학생 |
| **What (무엇을)** | 교내 분실물 등록 및 조회 웹 서비스 |
| **When (언제)** | 교내에서 물건을 습득하거나 분실했을 때 |
| **Where (어디서)** | 모바일 및 PC 웹 환경 (반응형) |
| **Why (왜)** | 신속한 분실물 반환 및 교직원의 분실물 관리 업무 부담 경감 |
| **How (어떻게)** | 습득자가 필수 정보를 기입하여 업로드하고, 분실자가 이를 조회하여 오프라인으로 수령 |

## 2. 각 기능 상세 정의

### 2.1 분실물 등록 (습득자용)
*   **사진 업로드 (Photo):**
    *   단말기 카메라 직접 촬영 또는 갤러리 이미지 업로드.
    *   제한: 최대 3장, 장당 5MB 제한. `.jpg`, `.png`, `.heic` 확장자 지원.
*   **습득 장소 (Found Location):**
    *   사전 정의된 카테고리(예: 식당, 운동장, 체육관, 화장실, 복도) 드롭다운 1차 선택 후 상세 텍스트(예: "2층 남자화장실 세면대") 입력.
*   **습득 시간 (Time):**
    *   `YYYY-MM-DD HH:mm` 형식의 Date/Time Picker 제공. 기본값은 시스템의 현재 시간.
*   **습득자 이름 (Finder's Name):**
    *   텍스트 입력 (인증 시스템 연동 시 자동 맵핑 및 수정 불가 처리).
*   **보관 위치 (Storage Location):**
    *   Radio 버튼 컴포넌트를 이용한 단일 필수 선택.
    *   옵션: `1학년 교무실`, `2학년 교무실`, `3학년 교무실`.

### 2.2 분실물 목록 및 상세 조회 (분실자용)
*   **목록 조회:**
    *   정렬: 등록일 역순(최신순) 기본 정렬.
    *   출력 항목: 썸네일 사진 1장, 습득 장소, 습득 날짜, 상태 라벨(보관 중/반환 완료).
    *   필터 및 검색: 보관 위치별 필터, 날짜 기간 필터, 텍스트 검색(장소 기준).
*   **상세 조회:**
    *   등록된 원본 사진(스와이프/캐러셀 형태), 습득 상세 장소, 습득 시간, 보관 위치 노출.
    *   습득자 이름은 가운데 글자 마스킹 처리하여 노출 (예: 홍*동).

### 2.3 상태 관리 (교직원용)
*   **상태 변경 (Status Update):**
    *   분실자가 물건을 수령해 갈 경우, 상태를 `보관 중`에서 `반환 완료`로 변경.
    *   상태 업데이트 시 완료 일시 및 처리자(교직원) 정보 DB 기록.

## 3. UX Flow

1.  **진입 (Main):** 메인 화면에서 [분실물 등록] 또는 [분실물 찾기] 분기.
2.  **분실물 등록 Flow:**
    *   [분실물 등록] 클릭 -> 사진 첨부 -> 장소/시간 입력 -> 습득자 입력 -> 보관 위치 선택.
    *   제출 전 "해당 교무실에 물건을 인계하셨습니까?" 확인 체크박스 동의 완료 후 [등록] 클릭.
    *   DB 저장 완료 후 메인 리스트로 리다이렉트.
3.  **분실물 찾기 Flow:**
    *   [분실물 찾기] 클릭 -> 리스트 뷰 진입.
    *   필터링을 통해 본인의 분실물 탐색 -> 리스트 아이템 클릭 -> 상세 뷰 진입.
    *   보관 위치(해당 학년 교무실) 확인 후 오프라인 이동.
4.  **반환 처리 Flow (교직원):**
    *   상세 뷰 진입 -> 학생 신원 확인 후 물건 인계 -> [반환 완료 처리] 버튼 클릭.

## 4. 기술 스택
*   **Frontend:** `React` (Next.js 권장 - 렌더링 최적화), `Tailwind CSS` (모바일 중심 반응형 UI).
*   **Backend:** `Node.js` (Express) 기반 REST API 또는 `Supabase` (BaaS 활용 시 인증 및 DB 백엔드 개발 공수 대폭 감소).
*   **Database:** `PostgreSQL` (관계형 데이터를 통한 정확한 상태 및 로그 관리).
*   **Storage:** `AWS S3` 또는 `Supabase Storage` (이미지 원본 및 썸네일 리사이징 저장).

---

## 5. MVP 로드맵 (4주 스프린트 기준)
*   **1주차 (설계):** DB 스키마(Item, User, Log 테이블) 설계, API 명세서 작성, 핵심 화면 와이어프레임 픽스.
*   **2주차 (백엔드):** 개발 환경 세팅, 스토리지 연동(이미지 업로드 API), CRUD 중심의 핵심 API 개발 완료 및 포스트맨 테스트.
*   **3주차 (프론트엔드):** 모바일 반응형 퍼블리싱, API 연동(목록 불러오기, 등록 폼 데이터 전송), 폼 유효성 검사 로직 구현.
*   **4주차 (QA 및 배포):** 통합 테스트, 이미지 업로드 용량 및 오류 대응, 클라우드(Vercel, AWS 등) 실서버 배포.

## 6. 리스크 및 대응 전략

| 리스크 | 대응 전략 |
|---|---|
| **장난성 허위 게시물 등록** | 학교에서 발급한 이메일 계정(`@school.ms.kr` 등)으로만 로그인할 수 있도록 Google OAuth 인증을 강제하여 익명성 남용 방지. |
| **습득자 개인정보 노출** | 상세 화면에서 일반 학생에게는 습득자의 이름을 마스킹(예: 김*수)하여 렌더링하고, 교직원 권한 계정에서만 실명을 확인할 수 있도록 프론트 및 API 응답을 분리. |
| **DB와 실제 보관 위치 불일치** | 글 등록 직후 발생하는 '물건 미인계' 상황을 방지하기 위해 등록 마지막 단계에 명시적인 동의 절차(체크박스)를 추가하여 습득자의 실물 인계 유도. |
